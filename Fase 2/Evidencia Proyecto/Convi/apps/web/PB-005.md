## Qué resuelve

Una persona que olvidó su contraseña puede solicitar un enlace por correo,
confirmarlo y definir una nueva contraseña para la identidad destinataria.
La respuesta pública no confirma si ese correo existe en CONVI.

Ejemplo: Ana olvidó la contraseña. Desde Login pulsa **¿Olvidaste tu contraseña?**,
escribe su correo y recibe el mismo aviso público que recibiría un correo sin
cuenta. Si Auth reconoce el correo y acepta el envío, llega el enlace. Al abrirlo
todavía no se consume: Ana pulsa **Continuar**, define y repite su nueva clave y,
si tiene TOTP vinculado, también confirma el código del autenticador.

Esto no recupera un autenticador perdido (PB-154), no reactiva una cuenta
suspendida (PB-153), no activa una invitación pendiente ni cambia un perfil.

## Reglas y recorrido

1. `/recuperar-contrasena` valida formato y largo del correo en el servidor,
   recorta sus espacios exteriores y lo pasa a minúsculas. Reutiliza el límite
   de 180 caracteres de los formularios públicos.
2. `solicitarRecuperacion` llama a `resetPasswordForEmail` con el cliente normal
   de Auth, sin clave administrativa. Para correos con formato válido siempre
   devuelve el mismo aviso, incluidos fallos, límites y errores del proveedor.
   No se consulta una lista de cuentas ni se crea una identidad inexistente.
   El aviso no es un comprobante de entrega; si no llega se puede esperar y
   solicitar otro enlace. Los límites de envío siguen siendo los de Supabase.
3. La plantilla usa `SiteURL` y `TokenHash`, no un destino aportado por el
   navegador. Abre `/restablecer-contrasena?...&type=recovery`.
4. Un GET solo muestra el botón **Continuar**: no verifica el token, no cambia
   la contraseña y no consume el enlace con una precarga o vista previa.
5. El POST `aceptarEnlaceRecuperacion` acepta exclusivamente `type=recovery`
   y llama a `verifyOtp`. Supabase comprueba destinatario, vigencia y uso único.
   Una verificación fallida no continúa aprovechando otra sesión ya abierta.
   Al aprobar, redirige a la misma ruta sin el token en la dirección.
6. `consultarRestablecimiento` y `restablecerContrasena` verifican la firma de la
   sesión con `getClaims` y consultan la identidad real con `getUser`.
   Auth también permite cambiar la contraseña propia desde una sesión existente;
   una persona ya autenticada puede entrar directamente a esta pantalla.
   La identidad siempre sale de Auth: ningún ID, correo, escuela o perfil del
   formulario decide a quién cambiarle la contraseña.
7. Con un TOTP confirmado y sesión `aal1`, el servidor elige un factor propio
   y pide los seis dígitos. `challengeAndVerify` confirma el factor antes de
   `updateUser`. No se elimina ni reemplaza ese factor para recuperar la clave.
   Una sesión que ya tiene `aal2` no necesita repetir el código en esta pantalla.
8. La contraseña debe tener al menos ocho caracteres y coincidir con su
   confirmación. No se recorta, porque sus espacios forman parte de ella.
   Los errores y estados enviados a la pantalla nunca incluyen contraseña,
   código ni respuestas completas de Auth. Auth conserva sus propias reglas
   adicionales de contraseña; una clave débil o repetida permite corregirla.
9. Solo después de que `updateUser` confirme el cambio se muestra éxito. Se
   intenta cerrar localmente esta sesión y se ofrece volver a Login mediante
   una navegación nueva. Si esa salida falla, se informa que la contraseña ya
   cambió y que falta cerrar la sesión; no se anuncia falsamente que el cambio
   falló. No se promete cierre inmediato de todos los JWT ya emitidos.
10. El siguiente login conserva PB-127/PB-009: escuela y membresía activas,
    perfil y MFA. Recuperar una clave no concede acceso al portal a una cuenta
    que el administrador haya suspendido.

## Base de datos: qué se utiliza, para qué y por qué

**Esta tarea no consulta ni modifica directamente ninguna tabla de `convi`.**
No necesita otra tabla de contraseñas o tokens. Usa el servicio Supabase Auth:

| Datos administrados por Auth                          | Uso en esta tarea                                                                                                                 | Por qué                                                                            |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Identidad de `auth.users`: `id`, `email`              | Auth reconoce el destinatario y el servidor compara el usuario con la identidad de la sesión.                                     | El formulario no puede elegir otro usuario para cambiarle la contraseña.           |
| Contraseña de `auth.users`: `encrypted_password`      | `updateUser` hace que Auth actualice el hash. El código no lee ni escribe esa columna por SQL.                                    | El hashing y las políticas de contraseña pertenecen a Auth.                        |
| Datos internos del enlace de recuperación             | `resetPasswordForEmail` y `verifyOtp` administran token, envío, vencimiento y consumo. El código no accede por SQL a esos campos. | No duplicar el mecanismo de enlaces de un uso en el modelo escolar.                |
| Sesión y tokens de Auth, representados en cookies SSR | Mantienen la identidad después de confirmar el enlace; `getClaims` verifica el JWT y `getUser` confirma el usuario.               | No basta con que el navegador afirme estar autenticado.                            |
| Factores de Auth: `id`, `factor_type`, `status`       | Selecciona un TOTP propio confirmado y lo verifica mediante la API MFA.                                                           | Conservar el segundo factor para cambiar la contraseña de una identidad protegida. |

Las tablas `convi.personas`, `membresias_establecimiento` y `establecimientos`
se conservan intactas: la persona no se duplica y su estado/perfil/escuela no
cambian. El login posterior usa esas tablas con las protecciones ya existentes.
No se añaden columnas, índices, políticas RLS, migraciones o privilegios.

## Configuración y comprobación

En local, `config.toml` define `[auth.email.template.recovery]`. Un Supabase
local que ya estaba iniciado necesita recargar su configuración de Auth antes
de enviar la plantilla nueva. Reiniciar solo web no actualiza las plantillas
del contenedor Auth. No ejecutar `db reset` para este cambio.

En cloud, guardar por separado **Reset password** con el HTML de
`supabase/templates/recuperacion.html` y asunto **Recupera tu contraseña de CONVI**.
`Site URL` debe ser el sitio publicado; no requiere un destino arbitrario ni
redirecciones nuevas porque el enlace se construye con esa URL configurada.
Subir el archivo a GitHub o publicar la web no actualiza esa plantilla del panel.

## Cómo explicarlo en una defensa

"PB-005 conecta dos pantallas con Supabase Auth. Una pide el enlace sin
confirmar si el correo existe; la otra verifica el enlace, la sesión y el
autenticador si está vinculado, y actualiza la contraseña de esa identidad.
La lógica está en recuperar-contrasena/acciones.ts. No agregué una contraseña
en personas ni cambié el estado de la membresía: recuperar acceso a Auth no
reactiva una cuenta suspendida de la escuela."
