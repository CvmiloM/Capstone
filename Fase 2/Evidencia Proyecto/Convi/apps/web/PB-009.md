# PB-009 — Exigir el segundo factor

Administración y Convivencia necesitan una cuenta activa, una escuela activa
y una sesión que haya confirmado el segundo factor (`aal2`). Profesor y
Apoderado pueden acceder a sus funciones sin este paso obligatorio.

## Cómo funciona

1. La web consulta `/auth/sesion` con la sesión de Supabase Auth. La API
   valida la identidad y resuelve la cuenta; el navegador no elige el perfil
   ni la escuela. La respuesta no se guarda en una caché compartida.
2. Si la cuenta necesita segundo factor, `/verificar-segundo-factor` consulta
   sus aplicaciones TOTP confirmadas. Sin una aplicación vinculada, ofrece
   continuar a `/segundo-factor`, la configuración de PB-008.
3. Con una aplicación vinculada, solicita su código actual de seis dígitos.
   El servidor elige un factor propio y confirmado, y vuelve a comprobar la
   cuenta antes de cada intento. No acepta un factor indicado por el cliente.
4. Supabase Auth verifica el código y escribe la sesión nueva en las cookies
   existentes. La web vuelve a consultar la API para confirmar que ya tiene
   `aal2`. Una respuesta fallida o incompleta no concede acceso.
5. El proxy renueva la sesión y comprueba su firma para Admin; sin sesión pasa
   al login y ante un error de Auth responde 503. Para Convivencia conserva la
   consulta previa de perfil y segundo factor. Las respuestas protegidas llevan
   `private, no-store`.
6. En Admin, cada lectura real pasa por un endpoint que exige cuenta y escuela
   activas, perfil ADMIN y `aal2`. No espera al encabezado ni a otra consulta de
   sesión para repetir esos mismos controles. Si la API rechaza con 403, la web
   consulta el estado para distinguir otro perfil, MFA pendiente y cuenta bloqueada
   y conservar las redirecciones. El resumen de ejemplo, que no consulta un endpoint,
   sigue comprobando la cuenta antes de mostrarse. No se cachean permisos entre
   solicitudes y cada operación conserva PB-127 y el aislamiento de escuela.

Una aplicación confirmada se conserva al iniciar otra sesión. Esta pantalla
no genera otro QR, no elimina factores y no guarda el código ni secretos en
CONVI, registros de consola o almacenamiento del navegador.

## Qué archivos lo hacen

- `src/lib/supabase/cuenta.ts`: consulta y valida la respuesta mínima de la API.
- `src/proxy.ts`: renovación de cookies, comprobación de sesión para Admin y
  control previo de acceso a Convivencia.
- `src/app/(publico)/verificar-segundo-factor/page.tsx`: lectura de sesión al
  llegar una petición, dentro de Suspense.
- `src/app/(publico)/verificar-segundo-factor/acciones.ts`: consulta de factores,
  validación del código y confirmación de la sesión con Auth y API.
- `src/app/(publico)/verificar-segundo-factor/formulario-verificacion.tsx`:
  pantalla con los componentes y colores existentes de CONVI.
- `src/app/admin/datos.ts`: lecturas Admin a endpoints autorizados y redirecciones
  al rechazar la sesión, sin encadenar innecesariamente encabezado y contenido.
- `src/app/admin/layout.tsx`: comentario actualizado sobre la protección.
- `src/app/(publico)/segundo-factor/formulario-segundo-factor.tsx`: el botón
  «Continuar» pasa a comprobar el acceso después de configurar la aplicación.
- `PB-008.md`: documentación ajustada a ese enlace de continuación.

## Prueba manual

1. Con una cuenta Admin o Convivencia activa, vincular una aplicación desde
   `/segundo-factor`, escanear el QR y confirmar su código.
2. Abrir una sesión nueva con esa misma identidad. Mientras PB-004 no tenga
   login, se puede preparar una sesión local temporal para esta comprobación.
3. Ir a `/admin` con Admin: debe aparecer la verificación antes del panel.
4. Escribir un código incorrecto: debe indicar el error y conservar el bloqueo.
5. Escribir el código vigente del teléfono: debe confirmar el acceso. Admin
   puede continuar al panel y recargarlo sin repetir la verificación mientras
   conserve esa sesión. La aplicación vinculada debe seguir siendo la misma.
6. Limpiar la cuenta y escuela ficticias cuando termine la prueba.
