# PB-127: autorización de CONVI

Trabajo de Sebastian: base común de autorización completada para el alcance
acordado, lista para su commit. Se reutilizan las tablas, funciones y restricciones
de Camilo. Este documento mantiene un único avance; Git lo maneja Sebastian.

El cierre cubre la infraestructura de la API actual y las comprobaciones sobre
el modelo real. Cada nueva consulta, cambio o descarga debe integrar esta base
en su propio backlog y comprobar su recorrido completo desde la petición.

## Qué está listo

La API comprueba el token y la identidad con Supabase, y resuelve la cuenta activa
en cada petición. La escuela y el perfil salen de la base, nunca de lo enviado
por el navegador. Una ruta sin permisos definidos se rechaza.

GET /auth/sesion recibe Authorization: Bearer <access_token> y devuelve cuenta,
escuela, perfil y necesidad de segundo factor. Acepta la sesión inicial para
preparar ese paso; no entrega estudiantes ni expedientes. GET / sigue público.

Respuestas: 401 para sesión inválida, 403 para acceso rechazado y 503 si no se
puede comprobar la sesión o completar la operación.

## Cómo lo usan los compañeros

Importar AuthModule en el módulo que necesita CuentaService. El servicio ya está
exportado. Declarar los perfiles de la ruta con @PerfilesPermitidos y usar
CuentaService.operar para acceder a la base.

Ejemplo para comprobar un curso antes de trabajar con él:

```ts
return this.cuentas.operar(
  peticion.sesion,
  { tipo: 'curso_reporte', id: cursoId, perfiles: ['PROFESOR', 'CONVIVENCIA'] },
  async (db) => {
    const resultado = await db.query(
      'SELECT id, nombre FROM convi.cursos WHERE id = $1',
      [cursoId],
    );
    return resultado.rows[0];
  },
);
```

La comprobación y las consultas del bloque usan la misma conexión. El servicio
vuelve a resolver la cuenta, fija identidad/cuenta/escuela/segundo factor y aplica
las restricciones por escuela. Comprueba el permiso antes de ejecutar el bloque.
Una cuenta o escuela suspendida no puede seguir operando. Si algo falla se
revierte la operación; el contexto se limpia al devolver la conexión.

Tipos disponibles:

- establecimiento: contexto de escuela y perfiles indicados. Para operaciones
  propias del establecimiento; no usarlo para saltarse permisos de estudiante/caso.
- estudiante: usa puede_ver_estudiante. El modelo permite Convivencia y
  apoderados con vínculo y permiso vigente, no todos los perfiles.
- caso: usa puede_ver_caso. Para apoderados también indicar estudianteId.
- curso_reporte: usa puede_reportar_curso; exige la asignación del profesor.

Los perfiles se declaran en código del servidor. Para cambiar un caso, por
ejemplo, el bloque debe admitir únicamente los perfiles que permiten ese cambio,
no reutilizar automáticamente los permisos de lectura.
Consultar solamente el registro autorizado y devolver los campos permitidos.
Estas comprobaciones no implementan los otros backlogs ni eliminan la necesidad
de revisar los permisos de cada futura operación.

@ConsultaSesion queda reservado al inicio del segundo factor.
@Publica se reserva a las rutas que realmente deben funcionar sin sesión.

### Cómo conectar una nueva operación

1. Importar AuthModule en el módulo de esa función e inyectar CuentaService.
2. Declarar en la ruta @PerfilesPermitidos con los perfiles de esa acción.
3. Obtener la sesión de peticion.sesion, creada por el servidor. El navegador
   no decide su escuela ni su perfil.
4. Ejecutar las consultas mediante CuentaService.operar. Dentro del bloque usar
   solo el cliente db recibido y el identificador del registro autorizado.
5. Validar los campos y las reglas de esa función y devolver únicamente los
   datos permitidos. Comprobar también los accesos rechazados en su backlog.

Ejemplos de elección del permiso:

| Acción                              | Permiso y perfiles del ejemplo                         | Trabajo dentro del bloque                                                                                   |
| ----------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Consultar un estudiante             | estudiante; CONVIVENCIA o APODERADO con acceso vigente | Leer únicamente ese estudiante y sus campos permitidos.                                                     |
| Modificar un caso                   | caso; CONVIVENCIA                                      | Validar el cambio y modificar únicamente ese caso. APODERADO no obtiene permiso de cambio por poder leerlo. |
| Descargar datos de un caso          | caso; CONVIVENCIA o APODERADO con estudianteId         | Obtener los datos permitidos y comprobar que pertenecen al caso autorizado antes de generar el archivo.     |
| Trabajar con un curso para reportar | curso_reporte; PROFESOR o CONVIVENCIA                  | Usar el curso autorizado; un profesor necesita asignación vigente.                                          |

La misma lista de perfiles de la acción debe usarse en la ruta y en operar.
La etiqueta establecimiento sirve para datos propios de la escuela; no
sustituye el permiso de estudiante o caso.

Ejemplo de lectura de un caso para preparar una descarga:

```ts
return this.cuentas.operar(
  peticion.sesion,
  {
    tipo: 'caso',
    id: casoId,
    estudianteId,
    perfiles: ['CONVIVENCIA', 'APODERADO'],
  },
  async (db) => {
    const resultado = await db.query(
      'SELECT id, codigo FROM convi.casos WHERE id = $1',
      [casoId],
    );
    return resultado.rows[0];
  },
);
```

Este ejemplo entrega solo dos campos del caso autorizado; no crea una descarga.
La función que genere el documento elegirá los campos permitidos para cada
perfil. También debe autorizar cada petición de descarga, aunque el archivo ya
exista. Si el archivo pertenece a otro caso, rechazarlo.

Ejemplo de autorización para un cambio de caso:

```ts
return this.cuentas.operar(
  peticion.sesion,
  { tipo: 'caso', id: casoId, perfiles: ['CONVIVENCIA'] },
  async (db) => {
    const resultado = await db.query(
      'UPDATE convi.casos SET resumen = $1 WHERE id = $2 RETURNING id',
      [resumenValidado, casoId],
    );
    return resultado.rows[0];
  },
);
```

Antes de este ejemplo, la función debe validar resumenValidado y las reglas
del cambio de caso, incluyendo su motivo cuando corresponda. Aquí se muestra
solo cómo unir el permiso y el cambio en la misma conexión.

## Configuración para el equipo

La API usa SUPABASE_URL, la clave pública de Supabase y SUPABASE_DB_URL.
No necesita la clave de administración de Auth para atender peticiones.

Instalar las dependencias del lockfile y aplicar las migraciones pendientes:

```powershell
docker compose exec api corepack pnpm --store-dir /root/.local/share/pnpm/store/v10 install --frozen-lockfile
npx.cmd --yes supabase@2.117.0 migration up --local
docker compose up -d --no-deps api
```

La tercera migración permite SET ROLE convi_backend en PostgreSQL 17.
Las consultas del servicio usan ese rol limitado, aunque la conexión local
sea postgres. No consultar tablas de negocio directamente con postgres.
Para nube se necesita una credencial dedicada; no copiar la contraseña local.
