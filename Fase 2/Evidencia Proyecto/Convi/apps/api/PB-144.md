# PB-144: minimización de datos por perfil

Responsable: Sebastian, HU-123, Sprint 1, rama `sebastian/pb-144`.

La API entrega los campos necesarios para cada operación y perfil, no una
ficha completa para que la pantalla oculte lo que no debe mostrar. Se conserva
la autorización de PB-127 y el aislamiento por escuela de PB-141.

## Respuestas actuales

| Operación y perfil                                | Datos permitidos                                                                  | Datos que no entrega                                                                         |
| ------------------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `GET /auth/sesion`, cualquier cuenta activa       | Perfil y dos indicadores de segundo factor                                        | IDs de escuela/membresía, identidad de Auth, correo, estudiantes o expedientes               |
| Administración, contexto del portal               | Nombre de la persona, escuela y año activo                                        | Situaciones, casos, participantes o adjuntos de convivencia                                  |
| Administración, ficha del estudiante              | Datos administrativos y de contacto, estado y matrículas                          | Descripciones de situaciones, expedientes, evidencias o decisiones de Convivencia            |
| Profesor, cursos                                  | ID, nombre, nivel, año, roles y cantidad de estudiantes de sus cursos vigentes    | Ficha administrativa del curso o cursos ajenos                                               |
| Profesor, estudiantes de un curso asignado        | ID, nombres, apellidos y código institucional                                     | RUT, nacimiento, teléfono, correo o dirección                                                |
| Profesor, categorías para registrar               | ID y nombre de categorías activas                                                 | Descripción administrativa de la categoría                                                   |
| Profesor, sus registros                           | Su reporte, participantes, evidencias que él aportó y aclaraciones dirigidas a él | Reportes ajenos, expediente del caso, responsable de Convivencia o rutas privadas de Storage |
| Convivencia, bandeja y revisión                   | Situaciones de su escuela y datos necesarios para revisarlas                      | Registros de otra escuela o las funciones administrativas de cuentas/importaciones           |
| Convivencia, selector de funcionarios informantes | ID de persona y nombre                                                            | Perfil, correo, teléfono o RUT del funcionario                                               |
| Apoderado, entrada actual                         | Confirmación de sesión y perfil                                                   | Nómina escolar, cursos de Profesor, fichas administrativas o bandeja de Convivencia          |

El ID de persona en los informantes de Convivencia sí es necesario: el formulario
lo envía para identificar a quien informó. La API vuelve a validar su relación
con la escuela y el origen, el navegador no decide el permiso.

Los campos retirados no tenían consumidores en las pantallas actuales. Se
actualizaron sus tipos de transporte, manteniendo el diseño y las funciones
existentes. `consultarCuentaActiva` de Next conserva únicamente los tres campos
comprobados, aunque una respuesta futura de la API traiga propiedades extra.

## Cómo continuar sin perder estas restricciones

- Declarar los perfiles de la ruta y usar `CuentaService.operar`, la escuela
  y la membresía salen de la sesión comprobada, nunca de parámetros del cliente.
- Seleccionar columnas explícitas según la operación, evitar `SELECT *` o
  `RETURNING *` sobre fichas y expedientes. Un tipo TypeScript no elimina
  propiedades del JSON en ejecución.
- El rol `convi_backend` y RLS separan escuelas, no sustituyen el filtro por
  autor/asignación ni una respuesta específica para el perfil.
- Administración puede corregir datos administrativos, ese permiso no le da
  acceso a un caso, tampoco a la bandeja o a los adjuntos de Convivencia.
- Una ruta futura de apoderados debe comprobar el estudiante concreto con
  `puede_ver_estudiante` y, para un caso, `puede_ver_caso` con ese estudiante,
  además de devolver una proyección específica sin otros estudiantes.
  Autorizar un caso compartido no autoriza a enviar todos sus participantes.
- No ampliar los perfiles de un endpoint de Convivencia para reutilizarlo en
  el portal de apoderados, la forma y el alcance de la respuesta son distintos.

## Verificación

Se usó una API Nest aislada con sus controladores, guard y `CuentaService`
reales, PostgreSQL local y RLS reales, dos escuelas ficticias y diez cuentas
(incluidos dos profesores por escuela). La comprobación de firma de Supabase
se sustituyó solo en esa instancia de prueba por identidades ficticias, no
se cambió la autenticación de la aplicación ni se usaron sesiones cloud.

Las comprobaciones verifican las claves exactas del JSON y el rechazo de
perfiles/escuelas no autorizados, no solo que la pantalla oculte un dato.
También cubren MFA pendiente, cuenta suspendida, asignación terminada,
evidencia propia frente a la de Convivencia, reporte ajeno frente a inexistente,
vínculo de apoderado terminado y acceso expirado o revocado. Los datos de las pruebas
se crean en una transacción local y se retiran con `ROLLBACK`, comprobando
los conteos originales, sin enviar correos ni subir archivos.

Resultado: 41 comprobaciones específicas correctas, 32 pruebas existentes
correctas, compilación y lint de API, tipos y lint de los tres archivos web
cambiados correctos. Se comprobó el formato de los servicios, el helper de
sesión y esta guía. No se repitió un login o QR manual para cada perfil.

Las pruebas auxiliares están fuera del repositorio, no se añaden dependencias,
migraciones ni archivos de prueba. Las pruebas existentes del equipo se
conservan. La guía de PB-127 refleja la respuesta reducida de la sesión.

## Alcance pendiente del portal de apoderados

Todavía no existen en la API las consultas de estudiantes/casos del portal de
apoderados, su entrada actual no muestra esos datos. Se verifican sus rechazos
actuales y los permisos por vínculo del modelo, esto no implementa ni valida
un portal de expedientes de apoderados o sus descargas. Al añadir esas funciones
en sus backlogs, se deben repetir estas comprobaciones sobre su respuesta real.
