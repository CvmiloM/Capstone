## Escenario (HU-112 CA1)

- Dos escuelas sintéticas de la semilla 2026: SINTETICA-2026-NORTE y SINTETICA-2026-SUR.
- Volumen: 2535 estudiantes, 10 005 situaciones, 2300 casos, 21 818 participaciones, 6215 matrículas, 10 612 revisiones y 7123 cambios de estado de casos.
- Carga: 20 sesiones concurrentes de Convivencia con segundo factor, 100 consultas por sesión, 2000 en total, más una consulta de calentamiento por sesión que no se cuenta.
- Mezcla: 35 % historial de estudiante, 20 % búsqueda de estudiante, 20 % búsqueda de expedientes (mitad por apellido y mitad por código) y 25 % historial de caso, con estudiantes, apellidos, casos y códigos reales de cada escuela.
- Cada sesión hace sus consultas una tras otra y las 20 sesiones corren en paralelo.

## Máquina y red

- Procesador Intel Core i7-12700K, 20 núcleos visibles para Docker y 15 GB de memoria en WSL2 (Linux 6.18), Node 22.23.4.
- Todo local: el ensayo corre dentro del contenedor de la API y la llama por localhost, y la API usa la base y Supabase Auth locales de Docker.
- Cada consulta incluye la verificación del token con Supabase Auth, la cuenta y el segundo factor en la base, la transacción con seguridad por fila y la respuesta completa.
- El ensayo no mide la red entre Azure (Brazil South) y Supabase (us-east-1), que agrega unos 130 ms por viaje a la base: en la nube los tiempos serán mayores y conviene repetir el ensayo allá antes del piloto.
- No se afirma capacidad ilimitada (HU-117 CA1): lo medido es este escenario, en esta máquina.

## Qué se cambió

La búsqueda de expedientes (PB-077) era la única consulta fuera del límite, y tenía dos causas:

- Los cursos de cada caso de la página salían de la vista convi.vw_cursos_contexto_caso, que Postgres calcula completa para toda la escuela cada vez que se filtra por un caso: una página con 50 casos tardaba unos 8 segundos solo en eso, ahora se leen por caso con los mismos cuatro caminos de la vista y sus índices, en unos 40 ms y con el mismo resultado en 200 casos comparados, sin cambiar la vista.
- La lista y los totales se leían con dos consultas que recorrían todas las situaciones y casos de la escuela, revisando la seguridad por fila en cada fila, ahora es una sola lectura que con un estudiante entra por sus participaciones, los detalles de la página viajan juntos a la base, y los totales y las páginas son iguales a los anteriores en 10 combinaciones de filtros comparadas.

No se cambió el modelo de datos ni la seguridad: las políticas, la vista y los permisos siguen iguales.

## Hallazgos para decidir después

- Las políticas de seguridad por fila llaman a convi.sesion_valida() en cada fila leída, y escritas como (SELECT convi.sesion_valida()) Postgres la evaluaría una vez por consulta con el mismo resultado, y en la prueba una búsqueda bajó de unos 155 ms a unos 25 ms: es una migración del modelo y queda como decisión del PO.
- La API usa el pool de 10 conexiones por defecto de pg: con 20 conexiones las demás consultas bajaron entre un 20 y un 35 % en la prueba, aunque no hizo falta para cumplir HU-112.

## Cómo repetirlo

El ensayo usa las escuelas del generador, que se crean una vez:

    docker compose exec api node apps/api/dist/herramientas/sinteticos/generar.js --semilla 2026

Y se corre así, solo contra la base, Supabase y la API locales:

    docker compose exec api node apps/api/dist/herramientas/ensayo-carga/ensayo.js

Acepta --sesiones, --consultas, --limite-ms, --semilla y --api, y termina con código 0 si se cumplen HU-112 y HU-117.

Para iniciar sesiones con segundo factor usa una cuenta de Convivencia sintética de cada escuela que no es la de acceso (convivencia@), le pone una clave aleatoria que no se muestra y un factor TOTP del ensayo, y al terminar borra ese factor y deja otra clave aleatoria que nadie conoce, y sus consultas son de lectura: no cambia expedientes.
